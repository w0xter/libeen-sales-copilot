# AI Task Brief — LIB-004 · Case Repository, revisión, eventos e idempotencia

**Estado:** pendiente, no implementada. **Origen:** [DAG V0](../DAG.md). **Repo:** `w0xter/libeen-sales-copilot`. **Rama sugerida:** `codex/lib-004`. **Responsable (rol):** Integrador. **Gate:** G1. **Dependencias:** [LIB-003](LIB-003.md). Estas son asignaciones de trabajo propuestas, no branches/PR ya existentes.

## 1. Task ID

`LIB-004`. Antes de empezar, comprobar que todas las dependencias se hayan integrado y superado sus gates; trabajar en su propio worktree.

## 2. Objective

Implementar un store V0 en memoria con revisiones condicionales, recibos idempotentes, reset y trazabilidad mínima de eventos.

## 3. User / business value

Permite recibir mensajes sin perderlos ante errores y evita que aprobaciones o cambios concurrentes corrompan el expediente.

## 4. Context

Un Case contiene mensajes, facts, hitos, acciones y origen. La V0 no requiere DB ni procesos múltiples, pero sí un puerto sustituible.

Fuentes que debe leer cuando sean relevantes: [AGENTS.md](../../../AGENTS.md), [contrato de integración](../../contracts/INTEGRATION_V0.md), [documentación funcional](../../README.md), [matriz AC](../ACCEPTANCE_MATRIX.md), [DAG](../DAG.md). No necesita Notion para ejecutar esta tarea.

## 5. Scope

Persistencia de mensajes entrantes validada; CAS por revision; idempotencia de misma carga; conflicto si mismo id distinto contenido; reset desde caso ficticio.

## 6. Out of scope

Ni event sourcing completo, ni SQLite, ni transacciones de varios servicios, ni interpretación del LLM ni lógica de M3.

No implementar funcionalidades no incluidas aunque sean técnicamente sencillas; preparar un Contract Change Request si se descubre una dependencia real nueva.

## 7. Functional requirements

`MESSAGE_RECEIVED` se conserva antes del análisis; evento duplicado no modifica hechos ni hitos; revisión obsoleta retorna conflicto.

## 8. Technical requirements

Firmas del puerto de LIB-002, serialización estable, `eventId` + fingerprint, invariantes de revisión y snapshot. Solo un proceso local.

## 9. Constraints

No prometer persistencia en reinicios ni seguridad concurrente entre workers de producción.

Reglas globales no dispensables: solo datos sintéticos; sin envío real ni aprobación financiera, con evidencia y revisión humana; trabajo limitado a su brief y rutas propias.

## 10. Acceptance criteria

- [ ] El caso recibe mensaje válido aunque el análisis externo falle después.
- [ ] Mismo eventId+payload retorna el mismo recibo sin nuevo efecto; payload distinto provoca IDEMPOTENCY_CONFLICT.
- [ ] Dos escrituras que parten de misma revision no se pisan: una devuelve REVISION_CONFLICT.
- [ ] Reset restaura exactamente el fixture del caso.
- [ ] Todos los cambios observables tienen tests apropiados (si aplica); los fallos y áreas no probadas están documentados.
- [ ] El resultado incluye un handoff con archivos, evidencias, validación y riesgos.

## 11. Validation expected

Pruebas de dominio/repo simulando eventos repetidos, carrera y reset; `pnpm test tests/unit/cases` o equivalente.

No asumir que todos los comandos existen: LIB-001 crea `pnpm test` y `pnpm typecheck`; ejecutar los realmente disponibles y reportar outputs verdaderos.

## 12. Risks and sensitive areas

El peligro es acoplar el repo con Next.js o guardar el estado de un modelo como si fuera hecho confirmado.

## 13. Instructions for the agent

Utilizar skills Superpowers pertinentes (TDD, debugging, code review, verificación) si están instaladas, sin reabrir discovery ni modificar el DAG. Dentro de la tarea autorizada, implementar y verificar de forma autónoma; solicitar autorización solo ante cambios de contratos compartidos, alcance/ownership o operaciones externas.
